# E2E Scalability Tests

The scalability tests measure BMO and Ironic performance under load. They live in
`test/e2e/scalability_test.go` and are labeled `scalability`.
They run in the fixture e2e job with the default number of hosts, because
`make test-e2e` does not filter by label by default. The Ironic jobs select the
`required` or `optional` tiers, which do not include them.

## Tests

| Test | What it measures | Works with fixture | Works with Ironic |
|------|-----------------|--------------------|-------------------|
| Enrollment | Time from creating N hosts to all being available | Yes | With fake hardware |
| Provisioning | Time to provision the same hosts (available → provisioned) | Yes | With fake hardware |

Both tests share one `Ordered` container. The hosts are created once, the
enrollment test waits for them to become available and the provisioning test
provisions the same hosts. The test client has no client-side rate limit, and
the tests poll with one `List` per tick, so the measured durations do not
depend on client-go's default of 5 QPS.

When Ironic is deployed (`DEPLOY_IRONIC=true`), both tests also measure the
Ironic API latency with their hosts registered. See
[Ironic API latency](#ironic-api-latency) and
[Ironic with fake hardware](#ironic-with-fake-hardware).

## Running

Use `BMO_KUSTOMIZATION` to deploy BMO with the scalability settings. See
[BMO deployment settings](#bmo-deployment-settings).

### Fixture (no Ironic)

```bash
BMO_KUSTOMIZATION=../../config/overlays/fixture-scalability \
SCALABILITY_NUM_HOSTS=100 \
GINKGO_LABEL_FILTER="scalability" \
make test-e2e
```

### Ironic with fake hardware

The tests create their hosts with BMC addresses of the form
`redfish+http://192.168.222.1:8000/redfish/v1/Systems/<uuid>`. The UUID and
the boot MAC address of host N are derived from N (`systemUUID` and
`macFromIndex` in `scalability_test.go`). A real Ironic contacts the BMC, so
these systems must exist. `BMC_PROTOCOL=fake` in `hack/ci-e2e.sh` sets up an
environment for this, without VMs:

- The sushy-tools fake driver serves one fake Redfish system per host. The
  config is generated by `hack/e2e/generate_sushy_fake_config.sh` from the
  number of hosts, and mounted with vbmctl (`test/e2e/config/vbmctl-fake.yaml.tmpl`).
- fake-ipa runs as a container on the host network and acts as the agent of the
  fake hosts.
- Ironic is deployed with `data/ironic-standalone-operator/ironic/overlays/e2e-fake`,
  which sets `agent.require_tls=false`, because fake-ipa is a plain HTTP server.
- BMO is deployed with `config/overlays/e2e-scalability`.

```bash
BMC_PROTOCOL=fake SCALABILITY_NUM_HOSTS=100 ./hack/ci-e2e.sh
```

This runs only the `scalability` label with one Ginkgo node. Specs that need a
real VM cannot run in this environment. With the standard lab
(`BMC_PROTOCOL=redfish` and similar) the scalability hosts fail registration,
because the BMC emulator does not serve these systems.

## Configuration

| Environment Variable | Default | Description |
|---------------------|---------|-------------|
| `SCALABILITY_NUM_HOSTS` | 10 | Number of BMH resources to create |
| `SCALABILITY_API_THRESHOLD_MS` | 5000 | Fail if any Ironic API call exceeds this (ms) |
| `SCALABILITY_API_MEASUREMENTS` | 5 | API calls per measurement point |

## BMO deployment settings

The tests do not modify the BMO deployment. They run against whatever BMO the
suite installed from `BMO_KUSTOMIZATION`, so BMO settings such as the
controller concurrency belong in the kustomization.

The `config/components/scalability` component sets `BMO_CONCURRENCY` in the
`ironic` ConfigMap, which the manager container loads as environment
variables. Two overlays apply it on top of the regular e2e overlays:

| Overlay | Based on |
|---------|----------|
| `config/overlays/fixture-scalability` | `config/overlays/fixture` |
| `config/overlays/e2e-scalability` | `config/overlays/e2e` |

The component sets it to 8, the upper end of BMO's default of
`min(NumCPU, 8)`. This keeps the result independent of the machine and never
lower than the default. Keep it below `PROVISIONING_LIMIT` (default 20). To test
a different concurrency, change `BMO_CONCURRENCY` in the component.
For other environments, such as a bare metal lab, include the component in
your own overlay, or set `BMO_CONCURRENCY` there directly.

With namespace-scoped BMO (`NAMESPACE_SCOPED=true`), the tests use the
`scalability` namespace from `config/overlays/e2e/scalability`. BMO only
watches namespaces listed in `WATCH_NAMESPACE`, so a custom overlay must
include that namespace and its RBAC.

## Ironic API latency

The API latency is measured during the enrollment and provisioning tests
rather than in a separate test, so it uses the Ironic nodes that BMO created
for the test hosts. Measurements are taken at these points:

| Test | Point | Phase in results |
|------|-------|------------------|
| Enrollment | All hosts are available | `Enrollment` |
| Provisioning | Right after all hosts were given an image, while BMO is provisioning them | `Provisioning` |
| Provisioning | All hosts are provisioned | `Provisioned` |

At each point the test calls node list `SCALABILITY_API_MEASUREMENTS` times,
and node get the same number of times for both the first and the last host.
Each test logs every snapshot as JSON and fails if the slowest list or get
call at any point exceeded `SCALABILITY_API_THRESHOLD_MS`.
Measurements are skipped when Ironic is not deployed.

## Notes

- All scalability tests are `Serial` and `Ordered` in the test code, so they
   run alone and in order even when Ginkgo uses multiple parallel workers.
- The Makefile leaves `GINKGO_LABEL_FILTER` empty, so `make test-e2e` runs
   the scalability tests too. Select only them with
   `GINKGO_LABEL_FILTER="scalability"`.
- If a test fails or times out, the resources are dumped to the artifacts
   folder before the hosts are deleted.
